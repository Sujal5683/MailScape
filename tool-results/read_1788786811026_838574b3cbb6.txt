     1→# EMAIL CONVERSATION & FOLLOW-UP INTELLIGENCE
     2→
     3→## FEATURE-ONLY IMPLEMENTATION PROMPT
     4→
     5→You are modifying an already-built production React + TypeScript institutional email intelligence application.
     6→
     7→This prompt covers ONE FEATURE ONLY:
     8→
     9→> **Conversation / Follow-Up Intelligence**
    10→
    11→Do not redesign the entire application.
    12→Do not replace the existing architecture.
    13→Do not rebuild unrelated features.
    14→
    15→Instead, integrate this capability deeply and cleanly into the existing application, preserving the current design system, architecture, performance model, existing features, and professional code standards.

    18→
    19→# 1. CORE PROBLEM
    20→
    21→An email should not always be treated as an isolated message.
    22→
    23→A real institutional email conversation may look like:
    24→
    25→```text
    26→Initial Email
    27→    ↓
    28→Reply
    29→    ↓
    30→Follow-up
    31→    ↓
    32→Reminder
    33→    ↓
    34→Clarification
    35→    ↓
    36→Updated information
    37→    ↓
    38→Final response
    39→```
    40→
    41→For example:
    42→
    43→```text
    44→Placement Office:
    45→"Internship Opportunity — ABC Corp"
    46→
    47→        ↓
    48→
    49→Student:
    50→"Could you clarify the eligibility?"
    51→
    52→        ↓
    53→
    54→Placement Office:
    55→"Students with CGPA > 7 are eligible."
    56→
    57→        ↓
    58→
    59→Student:
    60→"Is Civil Engineering included?"
    61→
    62→        ↓
    63→
    64→Placement Office:
    65→"Yes, Civil Engineering students are eligible."
    66→
    67→        ↓
    68→
    69→Final Reminder:
    70→"Last date to apply is tonight."
    71→```
    72→
    73→The application must understand that these messages are related.
    74→
    75→The user should not have to manually remember which email belongs to which conversation.
    76→
    77→---
    78→
    79→# 2. DO NOT REDUCE THIS TO SIMPLE GMAIL THREADING
    80→
    81→Gmail `threadId` should be used wherever available, but it must NOT be the sole intelligence mechanism.
    82→
    83→There are multiple ways emails can belong to the same real-world conversation:
    84→
    85→### Strong signals
    86→
    87→* Gmail thread ID
    88→* `Message-ID`
    89→* `In-Reply-To`
    90→* `References`
    91→* identical normalized subject
    92→* sender/recipient relationship
    93→* chronological proximity
    94→
    95→### Medium signals
    96→
    97→* same institutional sender
    98→* same recipients
    99→* subject with `Re:` / `Fwd:` / similar prefixes
   100→* references to the same event/deadline/opportunity
   101→* overlapping entities and keywords
   102→
   103→### AI/semantic signals
   104→
   105→* same topic
   106→* same opportunity/application/event
   107→* one message explicitly referring to another
   108→* clarification/update/reminder relationships
   109→* continuation of an earlier discussion even when subject changes
   110→
   111→Do NOT blindly merge emails just because their subjects look similar.
   112→

   115→# 3. CONVERSATION MODEL
   116→
   117→Introduce a first-class domain concept:
   118→
   119→```text
   120→Conversation
   121→```
   122→
   123→A conversation is not merely a Gmail thread.
   124→
   125→It represents the application's understanding of related communication.
   126→
   127→Conceptually:
   128→
   129→```text
   130→Conversation
   131→├── Conversation ID
   132→├── Account ID
   133→├── Subject / canonical title
   134→├── Participants
   135→├── Messages
   136→├── Message count
   137→├── First message
   138→├── Latest message
   139→├── Latest activity
   140→├── Status
   141→├── Category
   142→├── Importance
   143→├── Attachments
   144→├── Deadlines
   145→├── Action items
   146→├── Follow-up state
   147→├── AI summary
   148→└── Relationship metadata
   149→```
   150→
   151→Keep the existing `threads` concept if it is already implemented.
   152→
   153→Do NOT create a redundant competing model without first inspecting the current architecture.
   154→
   155→Extend the existing model where possible.

   197→# 5. DISTINGUISH THREAD VS RELATED CONVERSATION
   198→
   199→This distinction is extremely important.
   200→
   201→### Same thread
   202→
   203→Strong provider-level relationship.
   204→
   205→Example:
   206→
   207→```text
   208→Gmail threadId = X
   209→```
   210→
   211→### Same conversation
   212→
   213→The application determines that separate emails belong to the same real-world topic.
   214→
   215→Example:
   216→
   217→```text
   218→Thread A
   219→"Internship Opportunity — Google"
   220→
   221→Thread B
   222→"Updated Eligibility for Google Internship"
   223→
   224→Thread C
   225→"Reminder: Google Internship Deadline"
   226→```
   227→
   228→These might be separate Gmail threads but one institutional conversation.
   229→
   230→The UI must be able to show:
   231→
   232→```text
   233→1 Conversation
   234→3 Threads
   235→14 Messages
   236→```
   237→
   238→without destroying the original Gmail structure.

   312→
